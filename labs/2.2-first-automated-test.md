## Background

### Why Automate?

| Automate when a test is... | Keep manual when a test is... |
|---|---|
| Run often (every build, every deploy) | Run once or rarely |
| High-risk if it breaks (login, money) | Exploratory or about "how it feels" |
| Stable: the feature isn't changing weekly | On a UI that's still being redesigned |
| Tedious or data-heavy (many inputs) | Hard to check by machine (visual appeal, wording) |
| Needed in CI/CD as a gate | Cheaper to run by hand than to build and maintain |

Automation costs time to **build** and to **maintain**. It pays off through **repetition**.

### Types of Automated Tests

| Type | Tests | Speed | BookNook example | Where in this course |
|---|---|---|---|---|
| **Unit** | One function | Milliseconds | `calculate_discount` | Lab 2.1 |
| **API** | Endpoints, no browser | Fast | `POST /api/auth/login` returns 401 | Lab 2.4 |
| **UI (end-to-end)** | The app through a real browser | Slow | Log in and see your email in the header | **This lab**, Lab 2.3 |
| **Performance** | Speed and load | Varies | Search under 3s with 200 users (NF1) | Concept only |

Healthy suites have **many** fast unit tests, **some** API tests, and **few** slow UI tests. This is often drawn as the **test automation pyramid**.

### Choosing a UI Tool

| | Selenium | Cypress | Playwright |
|---|---|---|---|
| Languages | Java, Python, C#, JS, more | JavaScript/TypeScript | JS/TS, Python, Java, C# |
| Browsers | All major | Chrome, Edge, Firefox, Electron | Chrome, Edge, Firefox, WebKit (Safari engine) |
| Waiting | Manual waits | Automatic retries | Automatic waits |
| Debugging | Logs, screenshots | Interactive runner with time travel | Trace viewer |
| Best fit | Large multi-language orgs, legacy suites | Web apps, fast feedback, JS teams | Cross-browser coverage, multi-language teams |

Questions to ask: What language does the team use? Which browsers must we support (NF4)? Does it run in our CI? Can the team maintain it?

We use **Cypress**: BookNook is a JavaScript web app, and Cypress's interactive runner is the friendliest way to learn.

## Part 1: Set Up Cypress (10 min)

The Cypress project lives in [ui-tests/](../ui-tests/). It's already configured to point at `http://localhost:3000`.

1. Make sure BookNook is running in one terminal (`cd sample-app` then `npm start`).
2. In a **second** terminal, install Cypress:

   ```bash
   cd ui-tests
   npm install
   npx cypress install
   npx cypress verify
   ```

   `npx cypress install` downloads the Cypress app (~500 MB). Newer npm versions skip this step during `npm install`, so run it explicitly.

3. Look at [ui-tests/cypress.config.js](../ui-tests/cypress.config.js). `baseUrl` lets tests use short paths like `cy.visit('/login.html')`.

> **Troubleshooting:** If you see `bad option: --smoke-test`, your terminal has `ELECTRON_RUN_AS_NODE` set (common in VS Code). Clear it, then retry:
> - PowerShell: `Remove-Item Env:ELECTRON_RUN_AS_NODE`
> - macOS/Linux/Git Bash: `unset ELECTRON_RUN_AS_NODE`

## Part 2: Your First Test – TC-1.1 (10 min)

1. Create `ui-tests/cypress/e2e/login.cy.js`:

   ```javascript
   const USER = { email: 'qa.user@booknook.test', password: 'Passw0rd!' };

   describe('US1 – Log in', () => {
     it('TC-1.1 valid login takes user to catalog', () => {
       cy.visit('/login.html');

       cy.get('#email').type(USER.email);
       cy.get('#password').type(USER.password);
       cy.get('#login-btn').click();

       cy.location('pathname').should('eq', '/');
       cy.get('#user-email').should('have.text', USER.email);
       cy.contains('a', 'Log out').should('be.visible');
     });
   });
   ```

2. Compare it with TC-1.1 in Lab 1.3. Each line maps to a precondition, step, or expected result. The test name keeps the **TC ID** so the automated test traces back to its test case.
3. Open the interactive runner:

   ```bash
   npx cypress open
   ```

   Choose **E2E Testing**, pick **Chrome** (or Edge), then click `login.cy.js`.
4. Watch it run. Then click on each command in the left-hand log. Cypress **time-travels** to show the page at that moment.

| Command | Does |
|---|---|
| `cy.visit(path)` | Opens a page |
| `cy.get(selector)` | Finds element(s) by CSS selector |
| `cy.contains(selector, text)` | Finds an element containing text |
| `.type(text)` / `.click()` / `.clear()` | Acts like a user |
| `.should(assertion, value)` | Checks a result, **retrying** for up to 4 seconds until it passes |
| `cy.location('pathname')` | Reads the current URL path |
| `cy.request(method, url)` | Calls an API directly, without the browser UI |

## Part 3: Make It Fail on Purpose (5 min)

A test you've never seen fail is a test you can't trust.

1. Change the expected email in the `#user-email` assertion to `wrong@booknook.test` and save. Cypress reruns automatically.
2. Read the failure: the **expected vs. actual** values, the line number, and the page snapshot at the moment of failure.
3. Put the correct email back. Green again.

Now run the suite **headless**, the way CI will (Lab 3.3):

```bash
npx cypress run
```

No browser window opens; you get a summary table in the terminal. Failed tests save a screenshot to `cypress/screenshots/`.

## Part 4: Negative Tests and Clean State (10 min)

### Test isolation

Every test must start from a **known state** and must not depend on another test. BookNook has a reset endpoint for exactly this. Restructure your file so each test resets data and opens the login page:

```javascript
const USER = { email: 'qa.user@booknook.test', password: 'Passw0rd!' };

function login(email, password) {
  cy.get('#email').clear().type(email);
  cy.get('#password').clear().type(password);
  cy.get('#login-btn').click();
}

describe('US1 – Log in', () => {
  beforeEach(() => {
    cy.request('POST', '/api/test/reset');
    cy.visit('/login.html');
  });

  it('TC-1.1 valid login takes user to catalog', () => {
    login(USER.email, USER.password);
    // ...same three assertions as before
  });
});
```

The `login()` helper keeps each test short and puts the selectors in **one** place. If the login form changes, you fix one function, not twenty tests.

### Data-driven negative test (TC-1.2)

AC1.2 has two inputs that must behave the same way. Generate one test per row:

```javascript
  const badLogins = [
    { name: 'wrong password', email: USER.email, password: 'WrongPass1' },
    { name: 'unknown email', email: 'nobody@booknook.test', password: USER.password }
  ];

  badLogins.forEach(({ name, email, password }) => {
    it(`TC-1.2 ${name} shows a generic error`, () => {
      login(email, password);

      cy.get('#message').should('have.text', 'Email or password is incorrect.');
      cy.location('pathname').should('eq', '/login.html');
    });
  });
```

Add this inside the `describe` block and run. Then write **TC-1.4** (log out returns to the catalog and shows **Log in**) on your own. Hint: after logging out, look for `#login-link`.

## Part 5: Automate the Lockout – TC-1.3 (15 min)

Write **two** tests for AC1.3 on your own, based on TC-1.3's data table in Lab 1.3:

| Test | Steps | Expected |
|---|---|---|
| `TC-1.3 four failed attempts, then correct password, logs in` | 4 wrong passwords, then the correct one | Lands on the catalog (`/`) |
| `TC-1.3 account locks on the 5th failed attempt` | 5 wrong passwords, then the correct one | 5th attempt **and** the correct password both show "Account locked. Try again in 15 minutes." |

Tips:
- Use a plain JavaScript `for` loop to repeat the failed logins.
- After **each** failed attempt, assert the message before the next attempt. Otherwise Cypress may type the next password before the previous response arrives.
- Run your whole file twice in a row. Does the lockout test still pass the second time? Why? (Look at your `beforeEach`.)

### Security lens (5 min)

Some of your tests are **security tests** in disguise:

| Test | Protects against |
|---|---|
| TC-1.2: same message for a wrong email and a wrong password | **Account enumeration**: an attacker learning which emails have accounts |
| TC-1.3: lockout after 5 failures | **Password guessing** (brute force) |

Add one more. The `session` cookie must be **HttpOnly**, so a malicious script injected into a page can't read it and steal the login:

```javascript
it('session cookie is hidden from page scripts (HttpOnly)', () => {
  login(USER.email, USER.password);
  cy.location('pathname').should('eq', '/');

  cy.getCookie('session').should('have.property', 'httpOnly', true);
});
```

Run it. Then look at NF2 in [REQUIREMENTS.md](../sample-app/REQUIREMENTS.md). Which parts of NF2 can a UI test **not** check? How would you check them instead?

## Discussion Questions

1. Which Lab 1.3 test cases did your team choose **not** to automate? Why?
2. Your lockout test passes on its own, but what would happen without the `beforeEach` reset if the tests ran in a different order?

5. BookNook must support Safari (NF4). Does that change your view of the tool comparison?
6. Where does each automated test you wrote today sit on the test automation pyramid? Is that the right place?

---

## Key Takeaways

- Automate tests that run **often**, protect **high-risk** features, and cover **stable** behavior.
- Prefer the **cheapest level** that proves the behavior: unit, then API, then UI.
- Choose tools based on your team's language, required browsers, CI, and ability to maintain the suite.
- Every test needs a **known starting state**. Reset data instead of depending on test order.
- Watch every new test **fail once** so you know it can.
- A failing test that matches the spec has found a bug. That's the test doing its job.

### Discussion Notes

- **Q2:** Without the reset, a lockout test leaves `qa.user` locked for 15 minutes, so TC-1.1 fails if it runs afterward. The second run of the file fails too. This is the **shared state** antipattern (Lab 3.4).
- **Q3:** Fixed waits are slow when the app is fast and still flaky when it's slow. Retrying assertions wait **only as long as needed**.
- **Q5:** Cypress has no Safari support; Playwright's WebKit is the closest option. Tool choice follows requirements.
- **Q6:** All of today's tests are UI (top of the pyramid). Login is worth one or two UI tests; the rest of its rules could also be covered at the API level, which is faster.
