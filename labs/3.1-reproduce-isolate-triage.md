# Lab 3.1 – Reproduce, Isolate, Triage

**Duration:** ~55–60 minutes  
**Prerequisites:** BookNook running, Chrome or Edge, Postman or a terminal with `curl`, Labs 1.2 and 2.4 findings handy  
**Modules:** 9 (Issue Triaging and Debugging)

## Learning Objectives

By the end of this lab you will be able to:
- Use browser DevTools, server logs, and stack traces to gather evidence
- Reproduce a vague report and reduce it to minimal, reliable steps
- Isolate a defect to a layer: front end, API, or requirements
- Assign severity, priority, and category, and tell severity and priority apart
- Recognize duplicates, "works as designed," and requirement questions
- Communicate a defect to a developer clearly and without blame

---

## Scenario

BookNook opened to a small group of beta customers over the weekend. A developer also merged a "small search improvement" on Friday. It's Monday morning, and support has forwarded **six tickets**.

You're running triage. For each ticket, decide: Is it real? Where does it live? How bad is it? Who needs to act? The team's fix queue for this week depends on your answers.

---

## Background

### Debugging Tools

| Tool | Where | Shows you |
|---|---|---|
| **DevTools Console** | Browser, `F12` → Console | JavaScript errors and warnings in the page |
| **DevTools Network** | Browser, `F12` → Network | Every request: URL, status, request body, response body |
| **Server log** | Terminal running BookNook, or `sample-app/logs/booknook.log` | Each API request with status and time, logins, discounts, and errors with **stack traces** |
| **Direct API call** | Postman or `curl` | Whether the API is right **without** the front end in the way |

### Reading a Stack Trace

```
SyntaxError: Invalid regular expression: /(/i: Unterminated group     ← 1. what went wrong
    at new RegExp (<anonymous>)                                          ← 2. where it was thrown
    at searchPattern (...\sample-app\server.js:173:10)                   ← 3. first frame in OUR code
    at ...\sample-app\server.js:181:24                                   ← 4. who called it
    at Layer.handle (...\node_modules\express\lib\router\layer.js:95:5)  ← 5. framework, usually ignore
```

Read **top to bottom**: the error type and message, then the first frame in **your** code (`file:line:column`). Frames inside `node_modules` are the framework calling your code. The bug is rarely there.

### From Report to Root Cause

| Step | Goal | Ask yourself |
|---|---|---|
| **Reproduce** | See it happen yourself | Exactly what did the user do? What browser, account, data? |
| **Minimize** | Fewest steps, smallest input | Which step or value can I remove and still see it? |
| **Isolate** | Find the layer | Is the API response right? Then it's the front end. Wrong? It's the back end. No rule says what's right? It's requirements. |
| **Collect evidence** | Prove it | Log lines, stack trace, screenshot, Network response |

### Severity vs. Priority

| | **Severity** | **Priority** |
|---|---|---|
| Measures | **Impact** on the system or user | **Urgency** to fix |
| Set by | QA, from evidence | Product Owner and team, from business needs |
| Scale | Critical, High, Medium, Low | P1 (now) → P4 (someday) |

They don't always match:
- **High severity, low priority:** the app crashes in an admin report that runs once a year.
- **Low severity, high priority:** the company logo is misspelled on the home page during launch week.

### Triage Outcomes

| Outcome | Means | Next action |
|---|---|---|
| **New defect** | Real, not reported before | Report it (Lab 3.2) and send to the dev team |
| **Duplicate** | Same root cause as an existing bug | Link to the existing bug; add new evidence |
| **Works as designed** | Matches the spec | Reply to support with an explanation |
| **Requirements question** | The spec doesn't say, or says something questionable | Send to the PO for a decision |
| **Cannot reproduce** | You can't make it happen | Ask the reporter for specific missing information |

## Part 1: Guided Investigation – Ticket T1 (15 min)

> **T1** – *From: support. "Customer says searching for **C++** books does nothing. Search works fine for other books. Tried Chrome and Edge."*

### Reproduce

1. On the catalog, search for `C++`. What do you see on the page? Does anything change?
2. Search for `dune`. Does search work now?

The page doesn't show an error. That's why the customer said "does nothing." Silent failures are common, so you need the tools.

### Collect evidence

3. **Console:** search `C++` again. Note the red error message.
4. **Network:** click the `books?q=C%2B%2B` request. Record the **status code** and the **Response** body. (`%2B` is how `+` is encoded in a URL.)
5. **Server log:** find the `ERROR` lines. Copy the first **three** lines of the stack trace into your board. Which **function** and **line** in `server.js` threw?

### Isolate

6. Call the API directly, without the browser:

   ```bash
   curl "http://localhost:3000/api/books?q=C%2B%2B"
   ```

   Same result? Then the failure is in the **back end**. The front end's part of the bug is only that it shows nothing when an error comes back.

### Minimize

7. Find out **which input** triggers it. Try each one and record what happens:

   | Search | Result (status, number of books) |
   |---|---|
   | `C` | |
   | `C+` | |
   | `++` | |
   | `(` | |
   | `.` | |
   | `Clean Code` | |

8. Look at the stack trace's error message again: *Invalid regular expression*. What do `+`, `(`, and `.` have in common?

### Triage

9. Fill in T1 on your board: reproduced, minimal steps, layer, evidence, category, severity, priority, outcome. Is this a **new** defect, or a duplicate of a Lab 1.2 bug?

## Part 3: Triage Meeting and Developer Message (10 min)

1. **Rank the fix queue.** List the tickets that need a code fix in the order the team should fix them. Be ready to defend your top pick.
2. **Write a message to the developer** who merged Friday's search change about T1. Keep it under 120 words. Compare these two:

   ❌ *"Search is broken again!! Your change crashed the server. Please fix ASAP."*

   ✅ A good message says **what** happens, **how** to reproduce it in one or two steps, the **evidence** (status, stack trace line), the **impact**, and asks a **question** instead of assigning blame.

3. Write a short reply to support for **T4** that a customer would understand.

## Discussion Questions

1. T1's page showed no error at all. How many tools did you need before you understood what was happening?
2. Why is it worth calling the API directly before writing a bug report?
3. Which ticket was hardest to classify, and why?

---

## Key Takeaways

- Users describe **symptoms**. Triage turns symptoms into a **reproducible**, **isolated** defect with evidence.
- Read stack traces top-down; find the **first frame in your code**.
- Calling the API directly splits front-end bugs from back-end bugs in seconds.
- **Minimize** the input or steps until you see the pattern. That pattern points to the root cause.
- **Severity** is impact; **priority** is urgency. They often differ.
- Not every ticket is a bug: duplicates, works-as-designed, and requirement questions need different owners.
- Report **facts and evidence**, not blame. Ask questions.

### T1 – Search crash (new defect, call it B11)

- **Page:** results don't change; previous books stay on screen.
- **Console:** `Uncaught (in promise) Error: Something went wrong. Please try again.`
- **Network:** `500`, body `{"err":"E_INTERNAL","message":"Something went wrong. Please try again."}`
- **Stack trace:** `SyntaxError: Invalid regular expression: /C++/i: Nothing to repeat`, thrown in `searchPattern` at `server.js:173`, called from the `/api/books` route at `server.js:181`.

| Search | Result |
|---|---|
| `C` | 200, many books |
| `C+` | 200, 18 books (wrong: should match "c+" literally, i.e., none) |
| `++` | **500** |
| `(` | **500** (`Unterminated group`) |
| `.` | 200, **all 30** books (wrong) |
| `Clean Code` | 200, 1 book |

**Root cause:** Friday's change builds a regular expression from the raw search text (`new RegExp(q, 'i')`). Characters with special meaning in regex (`+ * ? ( ) [ ] . \`) either crash it or change the match. Fix: escape the input, or go back to plain `includes()`. The front end also needs to show an error when search fails.

### Expected Triage Board

| Ticket | Reproduced? | Layer | Category | Severity | Priority | Outcome |
|---|---|---|---|---|---|---|
| **T1** | Yes, every time with `C++` | **Back end** (plus front end hides the error) | Functional | High | P1–P2 | **New defect (B11)** |
| **T2** | Yes: apply `SAVE15` **twice** (e.g., double-click **Apply**). Log shows `codesOnCart=SAVE15,SAVE15` | Back end (API accepts repeat codes) | Functional | High | **P1** | **Duplicate of B5** |

Severity and priority within one step are fine if justified. Strong answers note that T2 and T6 cost real money (lost revenue; refunds and an unhappy customer), and that T1 hurts a bookstore whose catalog includes programming titles.

**Sample fix queue:** T2/B5 → T6/B9 → T1/B11 → T3/B7. T4 and T5 go to the PO, not the developers.

### Sample Developer Message (T1)

> Hi Sam, I think Friday's search change has a problem with special characters. Searching for `C++` returns a 500, and the page shows nothing. To reproduce: `GET /api/books?q=C%2B%2B`. The log shows `SyntaxError: Invalid regular expression: /C++/i: Nothing to repeat` from `searchPattern` (`server.js:173`). `(` also crashes, and `.` returns every book. Looks like the search text goes into `RegExp` unescaped? Customers are hitting it in beta, so I've marked it P1–P2. Happy to pair on it. Want me to write a regression test for these inputs?

### Sample Reply to Support (T4)

> Thanks for passing this on. Maria's account locked correctly: our log shows 3 failed attempts on Saturday evening and 2 more on Sunday morning, which together reach our limit of 5 in a row. The lock clears automatically after 15 minutes, or she can reset her password. We've asked the product team whether failed attempts should expire overnight.

### Discussion Notes

- **Q1:** Usually three: Console (something failed), Network (500 from the API), server log (the actual cause). Each layer adds detail.
- **Q2:** It splits front end from back end immediately, so the report goes to the right developer with the right evidence (T3 vs. T1).
- **Q4:** Lockout counters that never expire punish occasional typos over days. Security and usability need to balance. It's the PO's call, informed by QA and security.
- **Q6:** T2 → Lab 2.4 "Apply a second code" (TC-3.4) and the Lab 2.1 rules; T3 → Lab 1.2 scripted step S8; T6 → Lab 2.4 stretch "Add out-of-stock book"; T1 → **none**. Nobody tested special characters in search. Good candidate for a new data-driven test.
- Results from this board feed **Lab 3.2**, where the new defect B11 and the accessibility defects A1–A4 get full bug reports.
