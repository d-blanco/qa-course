## Background

### Anatomy of an Actionable Bug Report

| Field | Purpose | Good example |
|---|---|---|
| **Title** | What's wrong, where, under what condition. Searchable. | *Cart: $35.00 order gets free shipping (should be "over $35")* |
| **Environment** | So the dev can match your setup | Build/commit, browser + version, OS, URL, test account |
| **Preconditions** | State needed before step 1 | Empty cart; logged out |
| **Steps to reproduce** | Numbered, **minimal**, one action per step | 1. Add book 21. 2. Open the cart. |
| **Expected result** | What should happen, with the **source** | Shipping $4.99 (F6.3: free "over $35") |
| **Actual result** | What did happen. Facts, no opinions. | Shipping $0.00 |
| **Evidence** | Proof | Screenshot, Network response, log lines, stack trace |
| **Reproducibility** | How often | Always (5/5) or Intermittent (2/10) |
| **Severity / Priority** | Impact / urgency (Lab 3.1) | High / P1 |
| **Links** | Context | Support ticket, test case ID, related bugs |

Developers ask three questions about every bug: *Can I reproduce it? Do I know what "right" looks like? Is it worth fixing now?* A good report answers all three.

### Bad vs. Good

❌ *"Shipping is broken!! Fix please."*

✅

```markdown
**Title:** Cart: $35.00 order gets free shipping (requirement says "over $35")
**Environment:** BookNook local build, Chrome 141, Windows 11, http://localhost:3000
**Preconditions:** Empty cart
**Steps to reproduce:**
1. Add "Salt Fat Acid Heat" ($35.00) to the cart
2. Open the cart
**Expected:** Shipping $4.99, Total $39.99 (F6.3: free shipping on orders **over** $35)
**Actual:** Shipping $0.00, Total $35.00
**Evidence:** `GET /api/cart` returns `"subtotal": 3500, "shipping": 0`. Screenshot attached.
**Reproducibility:** Always (3/3)
**Links:** Lab 2.4 request "Shipping at exactly $35"
**Notes:** Orders above $35 (e.g., $36.98) correctly get free shipping. Possibly `>=` instead of `>`?
```

Notice the last line: QA can **suggest** a cause, but the report stands on the facts above it.

### Quality Metrics

| Metric | Formula | Tells you |
|---|---|---|
| **Execution rate** | tests run ÷ tests planned | How much of the plan you actually did |
| **Pass rate** | tests passed ÷ tests run | How healthy the build looks under test |
| **Defects by severity** | count of open defects per level | How bad the open problems are |
| **Defect density** | defects ÷ size (per feature, or per 1,000 lines of code) | Where the bugs cluster |
| **Defect detection percentage (DDP)** | found by QA ÷ (found by QA + found by customers) | How good testing is at catching bugs before users do |

No single metric tells the whole story. A 95% pass rate means little if the 5% that failed is checkout.

### Test Reports vs. Dashboards

- A **dashboard** is live. The team checks it daily: *what's open, how bad, who's on it?*
- A **test summary report** is a snapshot. It's written at a milestone, compares results to **exit criteria**, and ends with a **recommendation**.

### Same Ideas, Different Tools

This lab uses **GitHub Issues** with a **GitHub Project** as the tracker. The concepts carry over directly to the tools you'll meet at work:

| Concept | GitHub (this lab) | Jira | Azure DevOps |
|---|---|---|---|
| A bug | Issue with the `bug` label | Issue type **Bug** | Work item type **Bug** |
| Severity | Custom project field | Custom field (or labels) | Built-in **Severity** field |
| Priority | Custom project field | Built-in **Priority** | Built-in **Priority** |
| Saved search | Project **view** with a filter | **JQL** filter | **Query** |
| Dashboard | Project views + **Insights** charts | **Dashboard** with gadgets | **Dashboard** with widgets |

## Setup (8 min)

Use the GitHub repository you'll use for the CI pipeline in Lab 3.3. If you don't have one yet, create an empty repository now (e.g., `qa-course`). Lab 3.3 pushes your code and tests into it, so bugs and failing pipeline runs can link to each other.

1. **Bug template.** In the repository, create the file `.github/ISSUE_TEMPLATE/bug_report.md` (**Add file → Create new file**). Paste this header, then the [Bug Report Template](#bug-report-template) below it, and commit:

   ```markdown
   ---
   name: Bug report
   about: Report a defect in BookNook
   labels: bug
   ---
   ```

   Now **Issues → New issue → Bug report** starts every bug from the template with the `bug` label.
2. **Project.** From your profile, **Projects → New project → Table** (start from scratch), name it `BookNook Quality`.
3. **Fields.** In the table, click **+** at the end of the header row → **New field**:
   - `Severity`, type **Single select**: Critical, High, Medium, Low
   - `Priority`, type **Single select**: P1, P2, P3, P4
4. **Link them.** In the project's **⋯ → Settings**, confirm the project is linked to your repository (or link it from the repo's **Projects** tab).

When you file a bug, add it to `BookNook Quality` from the issue's right sidebar (**Projects**), then set **Severity** and **Priority** right there.

## Part 3: Build the Dashboard (10 min)

A GitHub Project has **views** (saved searches with a layout) and **Insights** (charts). Together they're your dashboard. Each view is a tab across the top of the project.

1. **Open bugs list.** Rename the default view (double-click its tab) to `Open bugs`. In the filter bar, enter:

   ```
   is:open label:bug
   ```

   Show the columns Title, Severity, Priority, Status, Assignees (**+** on the header row, or the view menu **▾ → Fields**). Sort by **Priority** (view menu **▾ → Sort by**). Save the view.
2. **Severity view.** **+ New view → Table**, name it `By severity`, same filter. View menu **▾ → Group by → Severity**. Each group header shows its count.
3. **Work board.** **+ New view → Board**, name it `Board`. Columns come from the built-in **Status** field (Todo, In Progress, Done).
4. **Chart.** Click **Insights** (the chart icon at the top right of the project) → **New chart**. Name it `Open bugs: severity × priority`, filter `is:open`, then configure it: Layout **Stacked column**, X-axis **Severity**, Group by **Priority**. Save.
5. On the board, drag one bug to **In Progress**. Then **close** a different bug as completed. Which views and charts changed after each step?

Your dashboard shows only the bugs **you** filed. The test summary report uses the team's full data.

---

## Key Takeaways

- A good bug report lets a developer **reproduce, understand, and prioritize** without asking you a question.
- Cite the **source** of the expected result: a requirement, acceptance criterion, or test case.
- Paste logs and stack traces as **text**; use screenshots for what the user sees.
- Link everything: support tickets, test cases, related bugs. Links turn a bug into a trail.
- Dashboards show **now**; test summary reports compare a milestone against **exit criteria**.
- Use several metrics together, and break them down by suite and feature. One overall number hides where the risk is.

### Part 3 – Dashboard

With B11, B5, B9, B7 (plus A3): `By severity` shows High 3–4, Medium 1 (B7). The chart has a tall High column split across P1/P2, and a short Medium column for B7 at P2. Two linked B11 issues add a Medium (front end).

- **In Progress:** only the Status column and the Board change. The bug is still open, so the list, the severity groups, and the chart don't change.
- **Closed:** the bug disappears from `Open bugs`, `By severity`, and the chart (all filter on open issues). On the Board it moves to **Done** automatically.

Common snags: the issue wasn't added to the project (it won't appear anywhere); Severity left blank (shows up as "No Severity"); the Insights filter left empty, so closed bugs still count. Point out that severity lives in a **dedicated field**, not a label. That's what makes the grouping and charts reliable, in Jira and Azure DevOps too.

### Discussion Notes

- **Q2:** DDP is 93% but the one escape is a 500 on a core feature that customers hit on day one. Count and severity of escapes both matter.
- **Q3:** Show both: overall rate for trend, and per-suite or per-feature rates for risk. 100% unit tests only proves the discount **function** works (Lab 2.1), not the app's discount **endpoint**.
- **Q4:** Planted bugs in 650 lines inflate it. Density is most useful for comparing features or releases **within** one product, not across products.
- **Q5:** Tag tests with the feature's risk priority (e.g., `@P1` in test names, or a Priority field on test cases), or report pass rate per feature.
- **Q6:** Deleting or skipping failing tests raises pass rate. Closing bugs as "won't fix," or merging several into one, lowers bug counts. Pair metrics with review.
- Lab 3.3 puts these suites into a CI pipeline, so pass rate becomes a number that updates on every push.
