The team lead wants that to stop: *"Every change runs the tests. If the tests fail, it doesn't merge."* You're building that pipeline today. Before the day is out, a teammate is going to open a pull request against your discount code. Your pipeline needs to be ready.

## Background

### QA in CI/CD

| Without CI | With CI |
|---|---|
| Tests run when someone remembers | Tests run on **every** push and pull request |
| Bugs found days later, cause unclear | Bugs found in minutes, tied to **one** change |
| QA tests at the end, as a phase | QA designs the checks; the pipeline runs them all the time |
| "Works on my machine" | Runs on a clean machine every time |

QA's job shifts from **running** tests to **designing** the safety net: which tests run, in what order, what blocks a merge, and what the feedback says.

### Pipeline Vocabulary (GitHub Actions)

| Term | Meaning | In this lab |
|---|---|---|
| **Workflow** | A YAML file in `.github/workflows/` | `qa-pipeline.yml` |
| **Trigger** (`on:`) | What starts it | Push to `main`, any pull request, manual run |
| **Job** | A group of steps on one fresh machine (**runner**) | `unit`, `api`, `ui` |
| **Step** | One command or action | `npm test` |
| **`needs:`** | Job order: wait for another job to pass | `api` and `ui` need `unit` |
| **Status check** | A job's pass/fail result shown on a pull request | ✅ or ❌ next to each job |

### Shift-Left and the Feedback Loop

Put the **fastest, most precise** tests first. If they fail, don't waste minutes on slower ones.

```
push ──► unit (seconds) ──┬──► api (≈1 min) ──┐
                          └──► ui  (≈3 min) ──┴──► ✅ merge allowed
```

The sooner a failure shows up, and the closer it is to the change that caused it, the cheaper it is to fix.

### Gate vs. Report

| | **Gate** (blocking) | **Report** (non-blocking) |
|---|---|---|
| A failure... | Turns the build red and blocks the merge | Is shown, but the build stays green |
| Use for | Tests that must pass on every change | Known, **tracked** defects; checks you're still tuning |
| Risk | A gate that's always red gets ignored | A report nobody reads |

BookNook still has its planted bugs, so some of your API and UI tests **fail on purpose** (Labs 2.2–2.4). A pipeline that's red on every push teaches people to ignore red. Part 3 is about handling that honestly.

## Part 1: The First Stage – Unit Tests (10 min)

1. Create `.github/workflows/qa-pipeline.yml` in the course root. Use the `unit` job for **your** track only.

   ```yaml
   name: QA Pipeline

   on:
     push:
       branches: [main]
     pull_request:
     workflow_dispatch:

   jobs:
     unit:
       name: Unit tests (discount rules)
       runs-on: ubuntu-latest
       defaults:
         run:
           working-directory: tdd-discount/python
       steps:
         - uses: actions/checkout@v7
         - uses: actions/setup-python@v7
           with:
             python-version: '3.12'
         - run: pip install -r requirements.txt
         - run: python -m pytest -v
   ```

   **JavaScript track:** replace everything under `defaults:` with:

   ```yaml
       defaults:
         run:
           working-directory: tdd-discount/javascript
       steps:
         - uses: actions/checkout@v7
         - uses: actions/setup-node@v7
           with:
             node-version: 22
         - run: npm install
         - run: npm test
   ```

   YAML is picky about indentation: use **spaces**, never tabs.
2. Commit and push:

   ```bash
   git add .github
   git commit -m "CI: run unit tests"
   git push
   ```

3. On GitHub, open the **Actions** tab. Click the running workflow, then the **Unit tests** job. Expand the test step.
4. Record on your [Pipeline Log](#pipeline-log): how long the **job** took and how long the **tests** took. Where did most of the time go?

## Part 3: Gate vs. Report (7 min)

Every push from now on will be red until the planted bugs are fixed. Split each suite into a **gate** (must pass) and a **report** (known defects, shown but not blocking).

1. **UI job:** replace the `Run specs` step with two steps and a screenshot upload:

   ```yaml
         - name: Smoke tests (gate)
           working-directory: ui-tests
           run: npx cypress run --browser chrome --spec "cypress/e2e/login.cy.js,cypress/e2e/catalog.cy.js"
         - name: Accessibility and known defects (report only)
           working-directory: ui-tests
           continue-on-error: true
           run: npx cypress run --browser chrome --spec "cypress/e2e/accessibility.cy.js,cypress/e2e/discount.cy.js"
         - name: Upload failure screenshots
           if: always()
           uses: actions/upload-artifact@v7
           with:
             name: cypress-screenshots
             path: ui-tests/cypress/snapshots/actual
             if-no-files-found: ignore
   ```

   (`discount.cy.js` is the Lab 2.2 stretch test. Leave it in the list even if you don't have it.)
2. **API job:** add `continue-on-error: true` to the `Run collection` step, rename it `Run collection (report only)`, and add a step that puts the **pass rate** on the run's summary page:

   ```yaml
         - name: Pass rate summary
           if: always()
           working-directory: api-tests
           run: |
             total=$(jq '.run.stats.assertions.total' results/api.json)
             failed=$(jq '.run.stats.assertions.failed' results/api.json)
             echo "### API tests: $((total - failed)) of $total assertions passed ($(( (total - failed) * 100 / total ))%)" >> "$GITHUB_STEP_SUMMARY"
             echo "Failures are known defects tracked in GitHub Issues." >> "$GITHUB_STEP_SUMMARY"
   ```

3. Commit (`CI: gate on smoke tests, report known defects`) and push. The run should be ✅. Open the run's **Summary** page and find the pass rate. Download the `cypress-screenshots` artifact and open one image.
4. **Link it.** Add a comment on one of your Lab 3.2 issues with a link to this run: *"Still failing in CI as of <run link>."*

**Stretch – the ratchet:** "report only" means a **new** API bug can slip through too. Add to the summary step: `if [ "$failed" -gt <today's failed count> ]; then echo "New API failures!"; exit 1; fi`. Now known failures are allowed, but **more** failures turn the build red.

## Part 4: The Teammate's Pull Request (15 min)

### Protect `main`

1. Your repository must be **public** for rules to be enforced on a free account (**Settings → General → Danger Zone → Change visibility**). If it must stay private, skip to step 3 and just watch the checks.
2. **Settings → Rules → Rulesets → New ruleset → New branch ruleset.** Name it `protect-main`, set **Enforcement** to **Active**, and under **Target branches** add **Include default branch**. Check **Require status checks to pass**, click **Add checks**, and add `Unit tests (discount rules)`, `API tests (Newman)`, and `UI tests (Cypress)`. Click **Create**.

### Play the teammate

3. On GitHub, open your `discount.py` (or `discount.js`) and click the ✏️ **Edit** button. Make the teammate's "cleanup," adapted to your code:
   - Find the line that **normalizes the code**. Remove the part that strips spaces, keep the uppercase. For example, `code.strip().upper()` → `code.upper()`, or `code.trim().toUpperCase()` → `code.toUpperCase()`. The teammate's reasoning: *"The UI already trims input."*
   - Find the **expiry check** and change `>` to `>=`. Reasoning: *"Codes should expire at the start of their expiry day."*
4. Click **Commit changes**. Message: `Simplify discount code lookup and expiry check`. Choose **Create a new branch for this commit and start a pull request**, name the branch `teammate/simplify-discount`, and click **Propose changes**, then **Create pull request**.

### Read the feedback

5. Watch the checks at the bottom of the pull request. What happens to `api` and `ui`? Why?
6. Click **Details** next to the failed unit job. From the log alone, record:
   - Which tests failed, and their **test case IDs**
   - The expected vs. actual value, or the error, for each
   - Which **spec rule** (Lab 2.1, The Spec) each failure protects
7. Is the **Merge** button available?

### Respond

8. Leave a review (**Files changed → Review changes → Request changes**). Use what you learned in Lab 3.1: facts, evidence, a question, no blame. Address the teammate's two reasons.
9. **Fix it** as the teammate: edit the file on the `teammate/simplify-discount` branch to undo both changes and commit. Watch the checks rerun. When all three are ✅, **merge** the pull request.

## Key Takeaways

- CI runs the tests on **every** change, on a clean machine, and ties each failure to one change.
- QA **designs** the pipeline: which tests, in what order, what blocks a merge, what gets reported.
- **Shift left:** fast, precise tests first. Slow stages wait for them.
- A red pipeline must mean something. Gate on tests that must pass; report known, tracked failures, and plan to promote them back.
- Required **status checks** turn "please run the tests" into "it can't merge until they pass."
- Read pipeline feedback like a stack trace: which job, which test, expected vs. actual, which change.

### Discussion Notes

- **Q1:** Machine start, checkout, and installs dominate. Speed-ups: dependency caching (`cache: npm` / `cache: pip` on the setup actions), running jobs in parallel (already done), running slow suites less often. Speed matters: slow feedback gets skipped or batched, and then failures can't be tied to one change.
- **Q2:** Alarm fatigue. Real failures hide among known ones, and people start merging on red.
- **Q3:** Every report-only test is linked to an issue (Part 3 step 4); the ratchet stops new failures; the team reviews the list regularly. When a bug is fixed, its test moves back to the gate **in the same pull request** as the fix. QA proposes it, the team agrees.
- **Q4:** Validation must live where the rule lives. Any client can call the API. B3 (case-sensitive codes) is the same class of bug.
- **Q5:** The `>=` change. The PR would still fail on TC-3.2, but a teammate who changed only the expiry check would have merged green. One boundary test is the only thing standing between `>` and `>=`.
- **Q6:** Here: one red check, a five-minute fix, no customer impact, no bug report needed. B11: customer tickets, triage, a bug report, a hotfix.
- **Q7:** Visual regression (needs CI baselines), cross-browser runs, the full accessibility scan, load tests. Run them nightly or before a release, not on every pull request.
- **Q8:** Sanity is narrow and about **this** change: search `C++`, `(`, `.`, then plain words, an empty search, and paging still work. Smoke is broad and shallow on **every** change: login and catalog still work. After the hotfix, smoke runs in the pipeline as usual, sanity confirms the fix, and the full regression suite runs before release. The new special-character tests then join regression for good.
- Lab 3.4 picks up the "random failure" thread: flaky tests that pass and fail without any code change.
