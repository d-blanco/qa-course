## Background

### What Is a Flaky Test?

A **flaky test** passes and fails on the **same code** without any change. It might depend on timing, on test order, on data, or on what another test left behind.

Why it matters:
- A pipeline is only useful if red means "something broke." Flaky tests teach people to ignore red.
- Every **Re-run** wastes minutes. Every ignored failure might be a real bug.
- Flaky tests get deleted, and the coverage goes with them.

### Five Common Causes

| Antipattern | Looks like | Why it's flaky | Reliable pattern |
|---|---|---|---|
| **Hard-coded wait** | `cy.wait(500)`, then a check | Fast machine: passes. Slow machine or network: fails. | Wait for a **condition**: `.should(...)` retries until true; `cy.intercept(...).as('x')` + `cy.wait('@x')` waits for a request |
| **Fragile selector** | `#results > div:nth-child(6) > button` | Breaks when the layout or data order changes, even though the feature works | Select by meaning: `data-cy` attributes, `cy.contains(selector, text)` |
| **Order dependence** | Test B uses a variable that test A set | Passes in order; fails alone, reordered, or in parallel | Each test sets up what it needs |
| **Random test data** | `Math.random()` picks the book | Fails only when the random pick hits a special case | Fixed, chosen data; one test per case you care about |
| **Shared state** | No reset between tests; one test leaves the server in a changed state | Passes alone; fails after another test runs | Reset in `beforeEach`, or use separate data per test |

### Cypress: Retrying vs. Not Retrying

```javascript
cy.get('.card').should('have.length', 1);       // retries for up to 4 s ✅
cy.get('.card').then($c => expect($c).to.have.length(1)); // checks ONCE ❌
```

`.should()` keeps querying the page and rechecking until it passes or times out. `.then()` runs once with whatever is on the page at that moment.

### Detection Tools

| Tool | How | Finds |
|---|---|---|
| **Rerun** | Run the same suite several times | Anything intermittent |
| **Isolate** | Change `it(` to `it.only(` and run just that test | Order dependence and shared state |
| **Burn-in** | Repeat one test many times in one run: `Cypress._.times(20, () => { it(...) })` | Low-probability flakes (random data) |
| **Slow it down** | `npm run start:slow` in `sample-app`: every API call waits a random 0–1.5 s | Timing problems hidden by a fast laptop |

### Test Reliability vs. App Reliability

"Reliable" means two different things in QA:

| | **Test reliability** (this lab) | **App reliability** (reliability testing) |
|---|---|---|
| Question | Does the test give the same answer for the same code? | Does the app keep working over time and when things go wrong? |
| Examples | Fixed waits, shared state, random data | Uptime (NF6: 99.5% in business hours), recovery after errors, running for hours (soak tests), surviving a failed dependency |
| BookNook | F1–F5 in this lab | B11 broke search, but the error handler kept the server up for everyone else (Lab 3.1) |

Slow mode is the simplest form of **fault injection**: make the environment worse on purpose and watch what breaks. It exposes fragile **tests** and fragile **apps** alike.

### Why Not Just Turn On Retries?

Cypress can retry failed tests automatically (`retries: 2`). That makes the build green, but the test is still flaky, and real **intermittent bugs** in the app get retried away too. Retries are a short-term bandage while you fix the cause, never the fix itself.

## Part 1: Detect and Diagnose (15 min)

### Rerun

1. Run `npm run flaky` **three times**. Record which tests fail in each run.
2. Which tests fail **every** time? Which fail **sometimes**? Which never fail?

### Slow it down

3. Stop BookNook and restart it in slow mode: `npm run start:slow`. The terminal shows `Simulated API latency: 0-1500 ms`.
4. Run `npm run flaky` **twice** more. Which test started failing that didn't fail before? Read its error message carefully.

### Isolate

5. Change `it('F5b ...` to `it.only('F5b ...` and run again. Does F5b pass on its own? Undo the `.only`.
6. Do the same for **F3b**. What happens, and why is the error message about `undefined`?

### Burn in

7. F4 might not have failed yet. Wrap **only F4** in a burn-in loop and run:

   ```javascript
   Cypress._.times(20, run => {
     it(`F4 a book can be added from its details page (run ${run + 1})`, () => {
       // ...F4's body, unchanged...
     });
   });
   ```

   How many of the 20 runs failed? Look at the failure screenshot in `cypress/snapshots/actual`. What is different about that book?

### Prove the fragile selector

8. F2 passes, so is it fine? In `sample-app/public/index.html`, find the **Add to Cart** button and wrap it in a `div`, a harmless layout change a designer might make:

   ```html
   <div class="actions"><button data-cy="add-to-cart" onclick="addToCart(${b.id}, 1)">Add to Cart</button></div>
   ```

   Run the suite. The feature still works (try it in the browser). Does F2? **Undo the change** (`git checkout -- sample-app/public/index.html`).
9. Fill in the **Diagnosis** table for F1–F5: when it fails, the antipattern, and your evidence.

## Part 2: Fix the Suite (20 min)

Fix every test in `shop.cy.js` so it passes **every** time, in **any** order, on a **slow** server. Keep what each test is meant to check. Rules:
- No `cy.wait(<number>)`, no bigger timeouts, no `retries`.
- Each test must pass with `it.only`.
- Prefer `data-cy` attributes, `cy.contains(...)`, and IDs that describe meaning (`#cart-count`) over structure.

Hints, if you're stuck:

| Test | Hint |
|---|---|
| **F1** | Replace the wait + `.then` with `.should`. Also: the page loads all books when it opens. What if that response arrives **after** your search results? Wait for the first load before you search (`cy.intercept('GET', '/api/books*').as('books')` before `cy.visit`, then `cy.wait('@books')`). |
| **F2** | Lab 2.3 Part 1 solved this exact problem. Also check the cart count by its ID. |
| **F3a/F3b** | One test, fixed data: click a **specific** book and check its details page. Delete the shared `chosenBook` variable. |
| **F4** | What is the test **for**? Pick specific in-stock books (try `forEach` over a few IDs). Then add a separate test that checks an **out-of-stock** book (ID 4) can't be added. That's a real requirement (F3.2), not an accident. |
| **F5a/F5b** | Move the reset into `beforeEach`. Then look at F5a: it clicks **Log in** five times without waiting for each answer. Intercept `POST /api/auth/login` and `cy.wait` for it after each click (or assert the message after each attempt, like `login.cy.js` in Lab 2.2). |

For each fix, write one line in the **Fixes** section of your log: what you changed and **why** it removes the flakiness.

## Key Takeaways

- A flaky test passes and fails on the same code. It costs trust, time, and eventually coverage.
- Detect it: rerun, isolate with `.only`, burn in, and slow the system down.
- **Wait for conditions, not time.** `.should()` retries; `.then()` doesn't. Wait on requests with `cy.intercept` + `cy.wait('@alias')`.
- **Select by meaning**, not by layout.
- Each test **owns its data and state**: reset in `beforeEach`, no shared variables, no random picks.
- Retries and longer timeouts hide flakiness; they don't fix it.
- Many QA antipatterns aren't about code: manual-only regression, ignored non-functional requirements, quarantines that never end, metrics that get gamed, and teams that don't talk.

### Fixed `shop.cy.js` (passed 45/45 in a 5-round burn-in on the slow server)

```javascript
const USER = 'qa.user@booknook.test';

function login(password) {
  cy.get('#email').clear().type(USER);
  cy.get('#password').clear().type(password);
  cy.get('#login-btn').click();
  cy.wait('@login');
}

describe('BookNook shop', () => {
  beforeEach(() => {
    cy.request('POST', '/api/test/reset');
    cy.intercept('GET', '/api/books*').as('books');
    cy.intercept('POST', '/api/auth/login').as('login');
  });

  it('F1 search finds The Pragmatic Programmer', () => {
    cy.visit('/');
    cy.wait('@books');
    cy.get('[data-cy=search-input]').type('prag{enter}');
    cy.wait('@books');

    cy.get('[data-cy=book-card]')
      .should('have.length', 1)
      .and('contain', 'The Pragmatic Programmer');
  });

  it('F2 adds Pride and Prejudice to the cart', () => {
    cy.visit('/');
    cy.contains('[data-cy=book-card]', 'Pride and Prejudice')
      .find('[data-cy=add-to-cart]')
      .click();

    cy.get('#cart-count').should('have.text', '1');
  });

  it('F3 details page shows the book that was clicked', () => {
    cy.visit('/');
    cy.contains('[data-cy=book-card] a', 'Clean Code').click();

    cy.get('h1').should('have.text', 'Clean Code');
  });

  [1, 6, 21].forEach(id => {
    it(`F4 in-stock book ${id} can be added from its details page`, () => {
      cy.visit(`/book.html?id=${id}`);
      cy.get('#add').click();

      cy.get('#message').should('have.text', 'Added to cart.');
    });
  });

  it('F4 out-of-stock book cannot be added from its details page', () => {
    cy.visit('/book.html?id=4');

    cy.get('#add').should('be.disabled');
  });

  it('F5a account locks after 5 failed logins', () => {
    cy.visit('/login.html');
    for (let i = 0; i < 4; i++) {
      login('wrong');
      cy.get('#message').should('have.text', 'Email or password is incorrect.');
    }
    login('wrong');

    cy.get('#message').should('have.text', 'Account locked. Try again in 15 minutes.');
  });

  it('F5b user can log in', () => {
    cy.visit('/login.html');
    login('Passw0rd!');

    cy.get('#user-email').should('have.text', USER);
  });
});
```

Accept other reliable fixes: e.g., F1 waiting with `cy.get('[data-cy=book-card]').should('have.length', 20)` before typing; F5 using `second.user@booknook.test` for the lockout test **and** resetting in `beforeEach`. Reject: `cy.wait(2000)`, raised `defaultCommandTimeout`, `retries`, or deleting the out-of-stock case from F4.

**Why F1 needs the first `cy.wait('@books')`:** in slow mode the page's initial "all books" request can finish **after** the search request and overwrite the results with 20 cards. Waiting for the first load before searching removes that race. This is also a small app bug (the page doesn't ignore stale responses). Good students mention it.

### Part 4 – Timing Checks

Measured: slow mode, **5 of 10** timing checks failed, average about 690 ms (min 16, max 1,492). With 0–1,500 ms of random delay, expect about two-thirds to fail on average. Normal mode: 0 of 10, average about 15 ms.

How to tell flaky timing from real slowness:
- **Look at the distribution, not one sample.** Rerun many times; compare the average and the 95th percentile with a known baseline from earlier builds.
- **Check the environment.** Was the CI runner busy, or the network slow? Do other, unrelated tests slow down too?
- **Check the server.** Logs (BookNook logs every request's duration), CPU, memory, database time. A real regression usually shows up in one endpoint, after one change.
- **Retest in a controlled environment** with a dedicated performance tool.

The lesson: a strict timing assertion is only as stable as the machine it runs on. In functional suites, keep timing thresholds generous (an early warning); measure real performance with percentiles, in a production-like environment, with tools built for it.

### Part 5 – Audit

| # | Antipattern | Risk | Fix |
|---|---|---|---|
| 1 | **Over-reliance on manual testing** for regression | Slow, skipped under pressure, human error; S8 found B7 only when someone noticed | Automate the stable scripted checks (Labs 2.2–2.4) in CI; keep humans on exploratory testing (Lab 1.2) |

### Discussion Notes

- **Q1:** In CI (Lab 3.3): shared runners are slower and busier than a laptop. That's why the pipeline waits with `until curl` instead of `sleep`.
- **Q2:** Any fixed wait is a guess. Too short: flaky. Long enough: every run pays the full wait even when the page is ready in 50 ms. Across hundreds of tests, minutes per run.
- **Q3:** No. It tested a random book each run and couldn't be reproduced. Better: a data-driven test over **chosen** books (Lab 2.2's data-driven pattern), or the API for many cases plus a few UI cases.
- **Q4:** Its result depends on what ran before it, not on the code. Reorder or run it alone and it passes. Same code, different result.
- **Q5:** 1 − (49/50)³⁰ ≈ 45% of days have at least one false red, about 0.6 per day. Ten such tests and nearly every day has false reds.
- **Q6:** When it duplicates coverage that exists at a lower level, or what it checks no longer matters. Never just because it's hard. Record the decision.
