# Lab 2.3 – UI Testing: Visual, Accessibility, Cross-Browser

**Duration:** ~55–60 minutes  
**Prerequisites:** Lab 2.2 completed (Cypress installed in `ui-tests/`), Chrome and Edge (Firefox optional), BookNook running  
**Modules:** 7 (User Interface Testing)

## Learning Objectives

By the end of this lab you will be able to:
- Choose locators that survive UI changes, and spot brittle ones
- Automate functional UI tests for search and paging
- Catch unintended visual changes with visual regression snapshots
- Run an automated accessibility scan against WCAG 2.1 AA and interpret the results
- Run the same tests across browsers and device sizes, and explain why results can differ

---

## Scenario

BookNook's launch is two weeks away. The PO has three new worries:
1. "Last release, a CSS change broke the product page and nobody noticed for a week."
2. "Legal says we must meet **WCAG 2.1 AA** (NF3)."
3. "Half our traffic is on phones, and we support Chrome, Edge, Firefox, and Safari (NF4)."

Functional tests alone won't catch any of these. You'll add three new kinds of UI checks to the suite.

## Background

### What UI Testing Checks

| Kind | Question | Tool in this lab |
|---|---|---|
| **Functional** | Does the UI **do** the right thing? | Cypress |
| **Visual** | Does it **look** the way it did? | `cypress-visual-regression` |
| **Accessibility** | Can **everyone** use it, including people using keyboards and screen readers? | `cypress-axe` (axe-core) |
| **Cross-browser / device** | Does it work in **every** supported browser and screen size? | Cypress `--browser`, `cy.viewport()` |

### Choosing Locators

UI tests break most often because a **selector** stopped matching, not because the app broke. Prefer selectors that are tied to **meaning**, not **layout**:

| Priority | Locator | Example | Breaks when... |
|---|---|---|---|
| ✅ Best | Dedicated test attribute | `[data-cy=search-input]` | Almost never; it exists only for tests |
| ✅ Good | Visible text the user sees | `cy.contains('button', 'Log in')` | The wording changes (often a real change) |
| ⚠️ OK | Stable `id` | `#email` | A developer renames it for styling or scripts |
| ❌ Avoid | Styling classes | `.btn-primary` | The design changes |
| ❌ Avoid | Position / structure | `#results > div:nth-child(3) > button` | Anything is added, removed, or reordered |

The BookNook team has started adding `data-cy` attributes to the **catalog** page: `search-input`, `category-filter`, `search-button`, `results`, `book-card`, `add-to-cart`, `page-info`, `prev-page`, `next-page`, `no-results`.

### WCAG in One Table

**WCAG 2.1** (Web Content Accessibility Guidelines) has four principles. Level **AA** is the usual legal and contractual target.

| Principle | Means | Example criterion |
|---|---|---|
| **Perceivable** | Users can perceive the content | 1.1.1 Images have text alternatives; 1.4.3 Text contrast at least 4.5:1 |
| **Operable** | Users can operate the UI | 2.1.1 Everything works from the keyboard; 2.4.7 Focus is visible |
| **Understandable** | Users can understand it | 3.3.2 Form fields have labels or instructions |
| **Robust** | Works with assistive technology | 4.1.2 Every control has a name and role |

Automated scanners catch roughly a third of accessibility issues. The rest need **manual** checks like keyboard-only use.

## Part 2: Functional UI Tests – Search and Paging (10 min)

Add a `describe` block for **US2**. Here's TC-2.1, data-driven for three search terms:

```javascript
describe('US2 – Search the catalog', () => {
  beforeEach(() => {
    cy.request('POST', '/api/test/reset');
    cy.visit('/');
  });

  ['prag', 'PRAG', 'Pragmatic'].forEach(term => {
    it(`TC-2.1 search "${term}" finds the book`, () => {
      cy.get('[data-cy=search-input]').type(`${term}{enter}`);

      cy.get('[data-cy=book-card]')
        .should('have.length', 1)
        .and('contain', 'The Pragmatic Programmer');
    });
  });
});
```

Now write these on your own, inside the same `describe`:

| Test | Check |
|---|---|
| `TC-2.3 empty search pages 20 books at a time` | Page 1: 20 cards, "Page 1 of 2", **Previous** disabled. Click **Next**: 10 cards, "Page 2 of 2", **Next** disabled |
| `TC-2.4 search with no matches shows a message` | Search `zzz`: `no-results` reads "No books found." and no `book-card` exists |

Hint: `.should('be.disabled')` and `.should('not.exist')`.

## Part 3: Visual Regression (10 min)

A visual test takes a screenshot and compares it, pixel by pixel, with an approved **baseline** image.

1. Create `ui-tests/cypress/e2e/visual.cy.js`:

   ```javascript
   describe('Visual regression', () => {
     beforeEach(() => {
       cy.request('POST', '/api/test/reset');
       cy.viewport(1280, 800);
     });

     it('book details page matches the baseline', () => {
       cy.visit('/book.html?id=1');
       cy.contains('h1', 'The Pragmatic Programmer').should('be.visible');
       cy.get('#login-link').should('be.visible');

       cy.compareSnapshot('book-details');
     });
   });
   ```

   The two `should` lines wait until the page has **finished loading**. Snapshotting a half-loaded page gives random failures.

2. Create the baseline **in Chrome**:

   ```bash
   npx cypress run --browser chrome --expose visualRegressionType=base --spec cypress/e2e/visual.cy.js
   ```

   Find the image in `cypress/snapshots/base/`. In a real project, baselines are reviewed and committed to Git.

3. Compare against it: run the same command **without** `--expose visualRegressionType=base`. It should pass.
4. Now simulate an "innocent" CSS change. In `sample-app/public/styles.css`, change the `.price` rule to:

   ```css
   .price { font-weight: bold; color: #1b7f3a; font-size: 1.3rem; }
   ```

5. Rerun the comparison. It fails. Open the image in `cypress/snapshots/diff/`. What changed besides the price?
6. **Revert** the CSS change and rerun. Green again.

> If a change is **intended**, you don't "fix" the test. You **approve** the new look by regenerating the baseline.

## Part 4: Accessibility Scan (15 min)

1. Create `ui-tests/cypress/e2e/accessibility.cy.js`:

   ```javascript
   const WCAG_21_AA = { runOnly: { type: 'tag', values: ['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa'] } };

   function logViolations(violations) {
     cy.task('log', `${violations.length} accessibility violation(s)`);
     cy.task('table', violations.map(v => ({
       id: v.id, impact: v.impact, description: v.description, nodes: v.nodes.length
     })));
   }

   describe('Accessibility – WCAG 2.1 AA', () => {
     beforeEach(() => {
       cy.request('POST', '/api/test/reset');
     });

     ['/', '/book.html?id=1', '/cart.html', '/login.html'].forEach(path => {
       it(`${path} has no WCAG 2.1 AA violations`, () => {
         cy.visit(path);
         cy.get('#account a').should('exist');
         cy.injectAxe();

         cy.checkA11y(null, WCAG_21_AA, logViolations);
       });
     });
   });
   ```

2. Run it headless so the violation tables print in the terminal:

   ```bash
   npx cypress run --spec cypress/e2e/accessibility.cy.js
   ```

3. For each violation, record the page, rule `id`, impact, and the **WCAG criterion** in the findings table. Use `npx cypress open` and click the failed assertion to see **which element** is affected.
4. The empty cart passed. But a cart is rarely empty. Add one more test that puts a book in the cart first (`cy.request('POST', '/api/cart', { bookId: 1 })`), then scans `/cart.html`. What does it find?
5. **Manual keyboard check** (automated tools can't do this one). On `/login.html`, put your mouse away:
   - Can you reach the email field, password field, and **Log in** button with **Tab**?
   - Can you always **see** where focus is?
   - Does **Enter** submit the form?

Don't fix the app. These are defects to report in Lab 3.2.

## Part 5: Cross-Browser and Cross-Device (10 min)

1. Run the functional catalog tests in two browsers:

   ```bash
   npx cypress run --browser chrome --spec cypress/e2e/catalog.cy.js
   npx cypress run --browser edge --spec cypress/e2e/catalog.cy.js
   ```

   Add `--browser firefox` if you have Firefox installed. Record the results.

2. Run the **visual** test in Edge against your **Chrome** baseline:

   ```bash
   npx cypress run --browser edge --spec cypress/e2e/visual.cy.js
   ```

   Chrome and Edge share the same engine. Does it pass? Look at the diff image.

3. Add a phone-sized test to `catalog.cy.js`:

   ```javascript
   it('catalog works on a phone-sized screen', () => {
     cy.viewport('iphone-x');
     cy.visit('/');

     cy.get('[data-cy=search-input]').should('be.visible');
     cy.get('[data-cy=book-card]').first().find('[data-cy=add-to-cart]').click();
     cy.get('#cart-count').should('have.text', '1');
     cy.document().its('documentElement.scrollWidth').should('be.lte', 375);
   });
   ```

   The last line checks for **horizontal scrolling**, a common mobile layout bug.

## Key Takeaways

- Use **test attributes** or **visible text** as locators; avoid layout-based selectors.
- Visual tests catch what functional tests miss, but need **stable pages** and **reviewed baselines**.
- Rendering differs by browser and OS. Keep **per-browser baselines** or allow a small **threshold**.
- Automated accessibility scans are fast and catch real defects, but cover only part of WCAG. Pair them with **manual keyboard checks**.
- Test pages in **realistic states** (cart with items, logged in), not just empty ones.
- Cross-browser and cross-device runs are cheap once tests exist. Run them in CI.

### Discussion Notes

- **Q1:** Titles aren't unique forever (new editions) and change with translations. Fine for a teaching app; use a `data-cy` with an ID in production.
- **Q2:** Options: per-browser baselines (most accurate), an `errorThreshold` (e.g., `cy.compareSnapshot('book-details', 0.05)`), or run visual tests in only one pinned browser in CI. Avoid thresholds so loose they hide real changes.
- **Q3:** Common approach: fail on `critical`/`serious` (`includedImpacts: ['critical', 'serious']`), report the rest. With a legal WCAG requirement, all four findings here should block release.
- **Q4:** The quantity field only exists when there are items. Scans only see what's on screen.
- **Q5:** Playwright's WebKit engine, a cloud device service, or a manual pass on a real iPhone or Mac.
- Visual and accessibility defects A1–A4 join B1–B10 for triage and reporting on Day 3.
