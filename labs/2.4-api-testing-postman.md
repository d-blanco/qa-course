# Lab 2.4 – API Testing with Postman

**Duration:** ~65–70 minutes  
**Prerequisites:** Postman desktop app with a free Postman account (or Thunder Client or `curl`; see the note in Setup), Node.js 22+, Lab 1.3 completed, BookNook running (see [sample-app/README.md](../sample-app/README.md))  
**Modules:** 8 (API Testing)

## Learning Objectives

By the end of this lab you will be able to:
- Describe the parts of a REST API call: method, URL, headers, body, and status code
- Send requests and write assertions in Postman
- Use environment variables and chain requests by passing data from one response to the next
- Write negative and data-driven API tests that find defects faster than UI tests
- Use JSON Schema checks as a light form of contract testing
- Stand in for an unbuilt endpoint with a Postman mock server
- Run a collection headless with Newman

## Scenario

The Lab 2.2 UI suite takes about 15 seconds to check six login rules. The team wants every **cart and discount rule** checked on every commit, in seconds. Most of those rules live in the REST API, so they can be tested **without a browser**.

Two more teams now depend on the API:

2. The **front-end team** wants to build the Order History page (F7) **now**, but the back end hasn't built `/api/orders` yet.

Your job: build a Postman collection that tests the BookNook API, checks its responses against a contract, and gives the front-end team a mock to build against.

## Background

### A REST Call in One Table

| Part | What it is | BookNook example |
|---|---|---|
| **Method** | The action | `GET` read, `POST` create, `PATCH` update, `DELETE` remove |
| **URL** | The resource, plus optional query parameters | `/api/books?q=prag&page=1` |
| **Headers** | Metadata about the request or response | `Content-Type: application/json`, `Set-Cookie: session=...` |
| **Body** | The data, usually JSON | `{ "bookId": 1, "qty": 2 }` |
| **Status code** | The result, as a number | `201 Created` |

### Status Codes You'll See Today

| Code | Meaning | BookNook example |
|---|---|---|
| `200 OK` | Success | Search results |
| `201 Created` | Something new was created | Book added to the cart |
| `400 Bad Request` | The request is invalid | Quantity 12 |
| `401 Unauthorized` | Not logged in, or wrong credentials | Wrong password |
| `404 Not Found` | No such resource | `/api/books/999` |
| `423 Locked` | The resource is locked | Account locked after 5 failed logins |
| `500 Internal Server Error` | The server crashed | Should never happen. Always a bug |

### What an API Test Checks

| Check | Question | Example |
|---|---|---|
| **Status** | Did it succeed or fail the right way? | `201`, not `200`, after adding to the cart |
| **Body values** | Is the data correct? | `discount` is `1200` for 15% off $79.98 |
| **Headers** | Is the response well formed? | `Content-Type` is JSON |
| **Schema** | Does the response have the agreed **shape**? | Every book has an integer `price` |
| **Response time** | Is it fast enough? | Under 500 ms |
| **Side effects** | Did it change what it should? | A follow-up `GET /api/cart` shows the book |

### Choosing an API Tool

| | Postman | REST Assured | Code-based (Supertest, Playwright, `cy.request`) |
|---|---|---|---|
| Style | GUI, plus JavaScript test scripts | Java library, fluent "given/when/then" | Tests in your app's language |
| Learning curve | Low | Medium (needs Java and a build tool) | Medium |
| Runs in CI | Yes, with **Newman** | Yes, with Maven/Gradle | Yes |
| Best fit | Exploring APIs, mixed-skill teams, sharing collections | Java teams, tests stored next to Java code | Teams who want API and UI tests in one suite |

The same check in REST Assured, for comparison:

```java
given().baseUri("http://localhost:3000").queryParam("q", "prag")
.when().get("/api/books")
.then().statusCode(200)
       .body("total", equalTo(1))
       .body("books[0].title", equalTo("The Pragmatic Programmer"));
```

We use **Postman**: no build setup, and the whole class can read a collection.

### Contracts and Mocks

The API's **provider** (the BookNook back end) and its **consumers** (the web front end, the mobile app) agree on a **contract**: endpoints, fields, types, and error formats.

| Technique | What it does | Today |
|---|---|---|
| **Schema validation** | Checks each response against a JSON Schema | Part 5 |
| **Consumer-driven contract testing** | Consumers publish what they need; the provider's build verifies it (e.g., **Pact**) | Concept only |
| **Mock server** | Returns saved example responses so consumers can work before the provider is ready | Part 7 |

## Part 2: Your First Assertions (10 min)

Postman tests are JavaScript that runs **after** the response arrives.

1. Change **Browse all books** back to `{{baseUrl}}/api/books` (no parameters). Open its **Scripts** tab, choose **Post-response**, and enter:

   ```javascript
   pm.test('Status is 200', () => pm.response.to.have.status(200));
   pm.test('Response is JSON', () => {
     pm.expect(pm.response.headers.get('Content-Type')).to.include('application/json');
   });
   pm.test('Responds in under 500 ms', () => pm.expect(pm.response.responseTime).to.be.below(500));

   const body = pm.response.json();
   pm.test('TC-2.3 page 1 shows 20 of 30 books', () => {
     pm.expect(body.total).to.eql(30);
     pm.expect(body.totalPages).to.eql(2);
     pm.expect(body.books).to.have.lengthOf(20);
   });
   ```

2. Send it and open the **Test Results** tab in the response pane. Four green passes.
3. **Make one fail on purpose:** change `30` to `31`, send, and read the failure message. Put it back.

| Code | Does |
|---|---|
| `pm.test(name, fn)` | Defines a named test |
| `pm.response.to.have.status(code)` | Checks the status code |
| `pm.response.json()` | Parses the body as JSON |
| `pm.expect(x).to.eql(y)` | Checks deep equality (Chai assertion library) |
| `.to.include(y)` / `.to.be.below(n)` / `.to.have.lengthOf(n)` / `.to.be.empty` | Other common checks |

4. Write these on your own, as new requests in `Catalog`. Keep the **TC ID** in the test name, as in Lab 2.2.

| Request | URL | Check |
|---|---|---|
| Search by partial title | `/api/books?q=prag` | `TC-2.1`: `total` is 1; first title is *The Pragmatic Programmer* |
| Page 2 | `/api/books?page=2` | `TC-2.3`: `page` is 2; 10 books |
| Search with no matches | `/api/books?q=zzz` | `TC-2.4`: `total` is 0; `books` is empty |
| Book not found | `/api/books/999` | Status 404; `err` is `E_NOT_FOUND` |

Notice what's **missing** compared with the UI: the API returns an empty list, and showing "No books found." is the **front end's** job. API tests check data and rules; UI tests check what the user sees.

## Part 3: Variables and Chaining (8 min)

Hard-coding `localhost:3000` and book IDs makes tests brittle. Variables fix that.

| Scope | Lives in | Use for |
|---|---|---|
| **Environment** | The selected environment | Things that differ per environment: `baseUrl`, test accounts |
| **Collection** | The collection | Values shared by all requests, such as defaults |
| **Data** | A CSV/JSON data file (Part 6) | Values that change each iteration |

If the same name exists at more than one scope, the narrower one wins: **data** beats **environment**, which beats **collection**.

### Chain a value from one response to the next

1. Add these lines to the end of **Browse all books**'s post-response script:

   ```javascript
   // Chain: save an in-stock book for later requests
   const book = body.books.find(b => b.stock > 0);
   pm.environment.set('bookId', book.id);
   pm.environment.set('bookPrice', book.price);
   ```

   Send it, then check the environment (eye icon). `bookId` and `bookPrice` are now set.

2. In the `Cart` folder, add **Add book to cart**: `POST {{baseUrl}}/api/cart`. On the **Body** tab choose **raw** and **JSON**:

   ```json
   {
     "bookId": {{bookId}},
     "qty": 2
   }
   ```

   Postman may underline `{{bookId}}` in red because it isn't valid JSON until the variable is filled in. That's fine. Add this post-response script:

   ```javascript
   pm.test('Status is 201', () => pm.response.to.have.status(201));
   const cart = pm.response.json();
   const price = pm.environment.get('bookPrice');
   pm.test('Line total and subtotal are price x 2', () => {
     pm.expect(cart.items[0].lineTotal).to.eql(price * 2);
     pm.expect(cart.subtotal).to.eql(price * 2);
   });
   ```

3. Send it. Then click **Cookies** (under the **Send** button). BookNook set a `cartId` cookie, and Postman will send it back automatically on every request to `localhost`. That's how the cart **remembers** you.
4. Write these on your own, in `Cart`:

| Request | Method and URL | Check |
|---|---|---|
| Get cart | `GET /api/cart` | Status 200; 1 item. This proves the add **persisted**: a side effect |
| Remove book | `DELETE /api/cart/{{bookId}}` | Status 200; `items` empty; `subtotal` and `total` are 0 |

5. In `Auth`, add **Login – valid**: `POST {{baseUrl}}/api/auth/login` with the body below. Test that the status is 200, the returned `email` equals `pm.environment.get('userEmail')`, and `pm.cookies.has('session')` is `true`.

   ```json
   {
     "email": "{{userEmail}}",
     "password": "{{userPassword}}"
   }
   ```

### Start from a known state

Add a **Reset data** request (`POST {{baseUrl}}/api/test/reset`, test: status 200) as the **first** request in each folder. Then run the collection: click the collection's **•••** menu, choose **Run**, and click **Run BookNook API**. Requests run **top to bottom**, so order matters.

## Part 5: Contract Testing with JSON Schema (8 min)

A **JSON Schema** describes the shape of a response: required fields and their types. If the provider renames `price` to `cost` or sends it as a string, every consumer breaks, even if the value is "right."

1. Add this to the **post-response** script of **Get cart**:

   ```javascript
   const cartSchema = {
     type: 'object',
     required: ['items', 'discounts', 'subtotal', 'discount', 'shipping', 'total'],
     properties: {
       items: {
         type: 'array',
         items: {
           type: 'object',
           required: ['bookId', 'title', 'price', 'qty', 'lineTotal'],
           properties: {
             bookId: { type: 'integer' },
             title: { type: 'string' },
             price: { type: 'integer' },
             qty: { type: 'integer' },
             lineTotal: { type: 'integer' }
           }
         }
       },
       discounts: { type: 'array', items: { type: 'string' } },
       subtotal: { type: 'integer' },
       discount: { type: 'integer' },
       shipping: { type: 'integer' },
       total: { type: 'integer' }
     }
   };
   pm.test('Matches the cart contract', () => pm.response.to.have.jsonSchema(cartSchema));
   ```

   Send it. It passes.

2. Now duplicate **Add book to cart**, rename it **Add book – non-numeric qty**, and change the body to `{ "bookId": 1, "qty": "abc" }`. Replace its script with the cart schema check above. Send it. Look at the body: what happened to `subtotal` and `total`? A value check might miss this. The schema doesn't.
3. Write a **book** schema on your own and add it to a new **Book details** request (`GET {{baseUrl}}/api/books/{{bookId}}`). Every field from Part 1 should be required, with the right type. `rating` is a number from 0 to 5.
4. **One contract for every error.** A consumer needs a predictable error format so it can show users a helpful message. Click the **collection** (not a request), open **Scripts**, choose **Post-response**, and enter:

   ```javascript
   // Contract: every error response is JSON with a code and a readable message
   if (pm.response.code >= 400) {
     const errorSchema = {
       type: 'object',
       required: ['err', 'message'],
       properties: {
         err: { type: 'string' },
         message: { type: 'string' }
       }
     };
     pm.test('Error response follows the error contract', () => {
       pm.response.to.have.jsonSchema(errorSchema);
     });
   }
   ```

   A collection-level script runs after **every** request in the collection. Run the whole collection. Which requests break the error contract? Which Lab 1.2 bug does this explain?

5. **Does the API match its documentation?** Go through the REQUIREMENTS.md REST API table. Send **one** request to each documented endpoint you haven't tested yet (for example, `POST /api/auth/register` and `GET /api/orders`). Record every mismatch between the docs and reality as a **contract finding** (C1, C2, ...) in the findings sheet. Look closely at what the docs say login "returns."

## Key Takeaways

- API tests sit **below** UI tests on the pyramid: faster, more stable, and close to the business rules.
- Check more than the status code: body values, headers, response time, schema, and side effects.
- Use **environment variables** for anything that changes between environments, and **chain** values instead of hard-coding them.
- **Negative** and **boundary** tests find most defects. Data files make them cheap to add.
- Write tests to the **spec**. A failing test that matches the spec has found a bug.
- A **schema** is a contract. Checking it catches breaking changes that value checks miss.
- **Mocks** let consumers work early, but they only prove the consumer works. The same contract must be checked against the real provider.
- **Newman** runs the same collection headless, ready for CI.

### Part 5 – Schema and contract

The non-numeric qty request returns 201 with `qty`, `lineTotal`, `subtotal`, and `total` all `null`. The schema fails with `data.subtotal should be integer` and similar errors. The server's `parseInt('abc')` gives `NaN`, which JSON turns into `null`.

    category: { type: 'string' },
    price: { type: 'integer', minimum: 0 },

Catalog tests that fail in a normal run (e.g., the error contract on Book not found) fail in every iteration too; that's expected. Why this doesn't prove NF1:
- **One user** sending requests one after another, not **200 concurrent** users

- **localhost** on a laptop, not production servers, network, and data volume
- 50 samples, a few seconds; load problems often appear only after minutes (memory, connection pools)

Real load tests use tools such as **k6**, **JMeter**, or **Gatling** in a production-like environment. This check is still useful: it's an early warning that runs on every commit. Lab 3.4 shows what happens to timing checks when the environment gets slow.

### Discussion Notes

- **Q1:** The answer-key collection runs 35 requests in about 3 seconds; Lab 2.2's six UI tests take about 15. UI tests are still needed for what the user **sees**: messages on screen (B10's display), the totals refreshing (B7), the catalog showing **Add to Cart** on out-of-stock books, and accessibility.
- **Q2:** The API is correct, so B7 is in the front end: `removeItem()` in `cart.html` calls `renderItems()` but not `renderSummary()`. Testing each layer separately **isolates** the defect. Lab 3.1 builds on this.
- **Q3:** Both. Without a documented error format, a developer could say there's no requirement. The QA engineer raises it; the PO and the team agree on the contract, then it's enforced by tests.
- **Q4:** No. Mocks prove the **consumer** works with the example. The real endpoint might use different field names, return cents vs. dollars, or require login. This is **mock drift**. Run the same contract tests against the provider (or use consumer-driven contracts such as Pact) so drift breaks a build, not production.
- **Q5:** The error contract check, or any negative test that asserts `message` exists. It fails at the API level, long before a user sees the raw error.
- **Q6:** The mobile app. Browsers store and send cookies automatically, so the web front end works. A native app coded against the docs looks for a token in the body and finds none.
- **Q7:** When the team writes Java and wants API tests in the same repo, language, and build as the service. Postman is better for exploring, sharing, and mixed-skill teams.
- API defects B1–B6 and B8–B10 join A1–A4 and the contract findings C1–C7 for triage (Lab 3.1). The Newman run is wired into CI in Lab 3.3.
