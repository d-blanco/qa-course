# Lab 1.1 – Test Strategy & Risk-Based Prioritization

**Duration:** ~45–60 minutes  
**Prerequisites:** VS Code (or any text editor), [sample-app/REQUIREMENTS.md](../sample-app/REQUIREMENTS.md)

## Learning Objectives

By the end of this lab you will be able to:
- Explain how QA, QC, and testing differ, and where each shows up in a test plan
- Spot requirements that are ambiguous or untestable before testing starts
- Score features by risk (likelihood × impact) and use the scores to prioritize testing
- Draft a one-page test plan with scope, approach, and entry/exit criteria
- Describe how a test plan changes under Waterfall, Agile, and DevOps

---

## Scenario

You have just joined **BookNook**, an online bookstore, as its only QA engineer. Release 1.0 launches in **4 weeks**, right before the holiday shopping season. There are 5 developers and 1 of you.

You cannot test everything equally. The Product Owner has asked for a one-page test plan by the end of the day that answers one question: **"What will you test first, and why?"**

---

## Background

### QA vs. QC vs. Testing

| | Quality Assurance (QA) | Quality Control (QC) | Testing |
|---|---|---|---|
| Focus | The **process** | The **product** | Specific **checks** |
| Goal | Prevent defects | Find defects | Execute a check, record a result |
| Example | Reviewing requirements for ambiguity | Inspecting a build before release | Running a login test case |
| When | Throughout the SDLC | After something is built | During development and QC |

A test plan is a QA activity: you are designing **how** quality will be achieved, before any testing happens.

### Risk-Based Testing

**Risk = Likelihood × Impact**

| Score | Likelihood (how likely is it to break?) | Impact (how bad if it breaks?) |
|---|---|---|
| 1 | Simple, stable, well understood | Cosmetic; nobody notices |
| 2 | Minor logic | Annoying, has a workaround |
| 3 | Moderate logic or some integration | Feature unusable for some users |
| 4 | Complex rules, many inputs, new code | Lost sales or a frustrated majority |
| 5 | Third-party integration, money, security | Data loss, security breach, legal or financial damage |

Things that raise **likelihood**: complex business rules, integrations with other systems, new or rushed code, vague requirements.
Things that raise **impact**: money, personal data, security, the number of users affected, brand reputation.

Highest scores get tested **first and deepest**. Lowest scores might get a quick smoke check, or be explicitly left out of scope.

## Part 1: Review the Requirements (10 min)

Good QA starts before any code exists. A requirement you cannot test is a defect in the requirements.

1. Open [sample-app/REQUIREMENTS.md](../sample-app/REQUIREMENTS.md) and read it end to end.
2. Create a new file named `my-test-plan.md` and copy the template from [The Template](#the-template) section below into it.
3. As you read, look for requirements that are:
   - **Vague:** no measurable pass/fail (e.g., words like "fast", "easy", "should")
   - **Incomplete:** missing a value or rule needed to test it
   - **Conflicting or unclear:** two rules that could interact in more than one way
4. Record **at least 5** in the **Requirement Questions** table of your template. For each, write the question you would ask the Product Owner.

> **Tip:** Ask yourself, "How would I know this passed?" If you can't answer, it's a question for the PO.

---

## Part 2: Score Features by Risk (15 min)

1. In the **Risk Assessment** table, score each feature F1–F8 for **Likelihood** (1–5) and **Impact** (1–5) using the scales in the Background section.
2. Calculate **Risk = L × I**.
3. Write a one-line **reason** for each score. The reason is more important than the number.
4. Sort the table from highest to lowest risk and assign a priority:

| Risk score | Priority | Test depth |
|---|---|---|
| 15–25 | **P1** | Test first; positive, negative, and edge cases |
| 8–14 | **P2** | Core flows plus key negative cases |
| 1–7 | **P3** | Smoke check only, if time allows |

> **Think about:** Which features touch money? Which involve a third party? Which have rules that interact with each other?

---

## Part 3: Draft the One-Page Test Plan (15 min)

Fill in the remaining template sections. Keep each one short; the whole plan should fit on one page.

1. **Scope:** What is in scope, and what is explicitly **out** of scope for 1.0? Saying what you won't test is as important as what you will.
2. **Approach:** For each priority level, which kinds of testing apply (functional, negative, exploratory, performance, security, accessibility)? Don't forget the non-functional requirements NF1–NF6.
3. **Entry criteria:** What must be true before testing starts? (e.g., build deployed to `qa`, test accounts created)
4. **Exit criteria:** What must be true before you recommend release? (e.g., no open P1 defects)
5. **Environments & data:** Which environment, and what test data do you need?
6. **Risks & assumptions:** What could derail the test effort itself?

---

## Part 4: The Methodology Lens (10 min)

The same plan looks very different depending on how the team works. In the **Methodology** table, describe in a sentence or two how **when** and **how** you test would change under each model.

| Model | Key traits to consider |
|---|---|
| **Waterfall** | Testing is a phase after development; requirements fixed up front |
| **Agile** | Short sprints; QA tests each story inside the sprint; requirements evolve |
| **DevOps** | Continuous delivery; automated tests run on every change; QA works with devs and ops |

## Discussion Questions

1. Compare your top three risks with a neighbor's. Where did you disagree, and whose reasoning was stronger?
2. Which vague requirement worries you most, and what could happen if nobody asks about it?
3. Your plan says some features are P3. How would you explain that choice to a stakeholder who owns one of them?
4. Which parts of your plan are QA (process), and which are QC (product)?
5. You have one QA engineer and 4 weeks. What is the most common pitfall a plan like this falls into?

---

## Key Takeaways

- QA starts **before** testing: reviewing requirements is the cheapest place to find defects.
- You can't test everything. **Risk = Likelihood × Impact** gives you a defensible way to decide what comes first.
- The **reason** behind a risk score matters more than the number.
- A good test plan states what is **out of scope** and has clear **exit criteria**.
- The methodology changes **when** testing happens and **who** does it, not whether quality matters.

### Plan Highlights

- **Out of scope (example):** the payment provider's own internals (we test our integration, not their system); load testing above 200 users; native mobile apps.
- **Approach:** P1 gets scripted positive, negative, and edge-case tests plus exploratory sessions. P2 gets core flows. P3 gets smoke checks. Non-functional work: security checks on F1/F6, an accessibility scan, a cross-browser pass, and a basic load check on search.
- **Entry criteria:** build deployed to `qa`; payment sandbox configured; test accounts and discount codes seeded.
- **Exit criteria:** all P1 tests pass; no open critical or high defects; P2 pass rate ≥ 95%; known issues signed off by the PO.
- **Risks to the test effort:** one QA engineer; unanswered requirement questions; payment sandbox availability; late code drops before launch.

### Methodology (sample)

| Model | How testing would change |
|-------|--------------------------|
| Waterfall | Full plan written up front; testing happens in a dedicated phase after the build; requirement questions must be resolved early because late changes are expensive. |
| Agile | Plan becomes a living document; each story is tested inside its sprint against acceptance criteria; risk is re-scored as the backlog changes. |
| DevOps | P1 flows become automated tests in the CI/CD pipeline that run on every change; QA works with devs on testability and shares ownership of quality. |

### Discussion Notes

- **Q4:** Reviewing requirements and defining entry/exit criteria are QA. Executing tests against a build is QC.
- **Q5:** Common pitfalls: spreading effort evenly instead of by risk; ignoring non-functional requirements; skipping out-of-scope decisions; not getting answers to requirement questions before testing starts.
