# Lab 1.3 – Writing Test Cases from User Stories

**Duration:** ~50–60 minutes  
**Prerequisites:** Labs 1.1 and 1.2 completed, BookNook running (see [sample-app/README.md](../sample-app/README.md))  
**Modules:** 3 (Functional and Non-Functional Testing), 4 (Writing Effective Test Cases)

## Learning Objectives

By the end of this lab you will be able to:
- Turn a user story into testable acceptance criteria using Given/When/Then
- Write clear, concise, reusable test cases that include negative and edge cases
- Tag test cases by test level (unit, integration, system, acceptance) and suite (smoke, regression)
- Build a traceability matrix and use it to find coverage gaps
- Explain the difference between acceptance criteria and the Definition of Done

## Scenario

The team is moving BookNook to Agile. The Product Owner has rewritten the requirements as **user stories** and answered several of your questions from Lab 1.1 in the **PO Notes**.

Before the sprint starts, the team needs acceptance criteria and test cases for each story. You'll write them, then hand two to a teammate to prove they are clear enough to run without you.

## Background

### User Story → Acceptance Criteria → Test Cases

| Artifact | Answers | Example |
|---|---|---|
| **User story** | Who wants what, and why? | *As a shopper, I want to apply a discount code so that I pay less.* |
| **Acceptance criteria (AC)** | When is **this story** done? | *Given an expired code, when I apply it, then I see "This code has expired."* |
| **Test case** | Exactly how do I check one AC? | Preconditions, data, steps, expected result |
| **Definition of Done (DoD)** | When is **any** story done? | Code reviewed, all AC tests pass, no open critical bugs |

### What Makes a Good Test Case

| Quality | Means | Avoid |
|---|---|---|
| **Clear** | Anyone on the team can run it | "Check the discount works" |
| **Concise** | One purpose per test case | Ten checks in one test |
| **Specific** | Exact data and exact expected results | "An error is shown" (remember S6 in Lab 1.2?) |
| **Reusable** | Shared preconditions; data in a table, not hard-coded in steps | Copy-pasting the same steps for every value |
| **Traceable** | Points to the AC it verifies | Orphan tests nobody can explain |

### Test Levels

| Level | Checks | BookNook example |
|---|---|---|
| **Unit** | One function in isolation | `calculateDiscount(7998, SAVE15)` returns 1200 |
| **Integration** | Components working together | Cart API correctly reads book prices from the catalog |
| **System** | The whole app, end to end | Add to cart → apply code → see correct total in the browser |
| **Acceptance** | The story meets the business need | The PO confirms the discount rules match the story |

Most test cases you write today are **system** or **acceptance** level. Tagging the level now helps decide later what to automate and where (Day 2).

### Test Suites

A suite is a group of test cases run together for a purpose. One test case can belong to several suites.

| Suite | When it runs | Scope | BookNook example |
|---|---|---|---|
| **Smoke** | Every new build or deploy | Broad and shallow: a few critical happy paths. "Is it alive?" | Catalog loads, login works, a book goes in the cart, a code applies |
| **Sanity** | After a small fix or change | Narrow and focused: "Did the fix work, and is the area right around it OK?" | After a fix to the $35 free-shipping rule: a $35.00 order, a cheaper one, a more expensive one |
| **Regression** | Before every release, or on every change in CI | Everything that used to work still works | All Regression-tagged cases |

Smoke asks "should we test this build at all?" Sanity asks "is this one change good?"

## Worked Example: US1 – Log In

> **US1:** As a registered customer, I want to log in so that I can check out and see my orders.
>
> **PO Notes:** Show the same message for a wrong email or a wrong password. Lock the account for 15 minutes after 5 consecutive failed attempts. A successful login resets the failed-attempt count.

**Acceptance Criteria**

- **AC1.1** Given a registered user, when they log in with a valid email and password, then they are taken to the catalog and the header shows their email and a **Log out** link.
- **AC1.2** Given a registered user, when they log in with a wrong password or an unknown email, then they stay on the login page and see "Email or password is incorrect."
- **AC1.3** Given a user with 4 consecutive failed attempts, when the 5th attempt fails, then the account is locked and they see "Account locked. Try again in 15 minutes."
- **AC1.4** Given a logged-in user, when they click **Log out**, then they are returned to the catalog and the header shows **Log in**.

**Test Cases (two of them)**

```markdown
### TC-1.1 Valid login takes user to catalog
- Story/AC: US1 / AC1.1
- Level: System    Type: Positive    Suite: Smoke, Regression    Priority: P1
- Preconditions: User qa.user@booknook.test / Passw0rd! exists and is not locked
- Steps:
  1. Go to the login page
  2. Enter the email and password
  3. Click Log in
- Expected: Catalog page is shown; header shows "qa.user@booknook.test" and "Log out"

### TC-1.3 Account locks on the 5th failed attempt
- Story/AC: US1 / AC1.3
- Level: System    Type: Negative, Edge    Suite: Regression    Priority: P1
- Preconditions: User qa.user@booknook.test exists with 0 failed attempts
- Test data:
  | Failed attempts | Then log in with correct password | Expected                                |
  |-----------------|-----------------------------------|-----------------------------------------|
  | 4               | Yes                               | Login succeeds; attempt count resets     |
  | 5               | Yes                               | "Account locked. Try again in 15 minutes." |
- Steps:
  1. Log in with a wrong password the number of times in "Failed attempts"
  2. Log in with the correct password
- Expected: As shown in the test data table
```

Notice how **TC-1.3** tests both sides of the boundary (4 and 5) with **one** set of steps and a data table. That's what makes it reusable.

## Part 1: Write Acceptance Criteria (15 min)

Create a file named `my-test-cases.md` and copy the [Template](#template) into it.

For **US2** and **US3** below, write 3–5 acceptance criteria each in Given/When/Then form. Use the PO Notes. Every AC must have a result you could check as pass/fail.

> **US2 – Search the Catalog:** As a shopper, I want to search for books by title or author so that I can quickly find what I want to buy.
>
> **PO Notes:** Matching is case-insensitive and partial ("prag" finds *The Pragmatic Programmer*). Results show 20 per page. An empty search shows all books. If nothing matches, show "No books found."

> **US3 – Apply a Discount Code:** As a shopper, I want to apply a discount code in my cart so that I pay less.
>
> **PO Notes:** Codes are **not** case-sensitive and ignore leading/trailing spaces. One code per order; applying a new code replaces the old one. Invalid codes show "That code isn't valid." Expired codes show "This code has expired." The discount can never exceed the cart subtotal.

**Stretch (if time allows):**

> **US4 – Rate a Book:** As a logged-in customer, I want to give a book a star rating so that other shoppers can benefit from my opinion.
>
> **PO Notes:** Must be logged in. 1–5 stars, required. Optional review text, max 1,000 characters. One rating per customer per book; rating again replaces the old rating. The average is shown to one decimal place.

## Part 2: Write Test Cases (20 min)

1. Write **at least 4 test cases each** for US2 and US3, using the test case format from the worked example.
2. Across your test cases, include at least:
   - one **positive** (happy path) case per story
   - two **negative** cases (invalid input, wrong state)
   - two **edge** cases (boundaries, e.g., 20 vs. 21 search results, discount vs. subtotal)
3. Tag each case with **Level**, **Type**, **Suite**, and **Priority**. Use the smoke suite only for a handful of the most critical happy paths.
4. Use a **test data table** wherever several values share the same steps.

> **Tip:** BookNook is running. Use it to look up real data for your test cases (book titles, prices, how many books are in a category). The catalog has 30 books.

---

## Part 3: Traceability and Coverage (10 min)

1. Fill in the **Traceability Matrix**: one row per AC, listing the test cases that cover it.
2. Mark any AC with **no** test case as a **gap**. Write a test case for it, or explain why it isn't needed.
3. Fill in the **Definition of Done check**: for each DoD item, is it proven by your test cases, or by something else?

**BookNook Team Definition of Done**

1. Code is peer-reviewed and merged
2. Every acceptance criterion has at least one passing test
3. Regression suite passes
4. No open critical or high-severity defects
5. Accessibility check passes (WCAG 2.1 AA)
6. Product Owner accepts the story

---

## Part 4: Peer Dry Run (5–10 min)

1. Swap files with a partner. Pick **two** of their test cases that BookNook can run today (US2 or US3).
2. Run them **exactly as written** against BookNook. Don't ask the author for help.
3. Record: Did you get stuck? Was the expected result specific enough to call pass or fail?
4. Give the author one piece of feedback per test case.

Working alone? Wait 5 minutes, then run two of your own test cases as if a stranger wrote them.

## Discussion Questions

1. What's the difference between an acceptance criterion and a test case? Could one AC need several test cases?
2. Which of your test cases would you run as a **smoke** test after every deploy? Why only those?
3. Which DoD items can **never** be proven by a test case? Who owns them?
4. Your partner got stuck on one of your test cases. What was missing?
5. Run your US3 test cases against BookNook. How many of the Lab 1.2 bugs would they have caught?
6. Which of your test cases look like good candidates for automation tomorrow?

---

## Key Takeaways

- Acceptance criteria turn a story into **testable** statements; test cases say exactly **how** to test them.
- A good test case is clear, concise, specific, reusable, and **traceable** to an AC.
- **Data tables** make one test case cover many boundary values without duplication.
- A traceability matrix shows coverage at a glance, and shows **gaps** before users find them.
- Acceptance criteria are per story. The **Definition of Done** applies to every story, and some of it isn't testing at all.

### Traceability and Gaps

- AC2.4 (empty search) is often missed, but TC-2.3 covers it. Point out that one test case can trace to more than one AC.
- AC3.6 is the most commonly missed; it maps to Lab 1.2 bug B6.
- Unit-level candidates: the discount math in AC3.1 and AC3.6 is pure calculation and belongs in a unit test. That's the setup for Lab 2.1 (TDD).

### Definition of Done Check

| DoD item | Proven by test cases? | Otherwise proven by |
|----------|-----------------------|---------------------|
| 1 Code reviewed | No | Pull request approval |
| 2 Every AC has a passing test | **Yes**, via the traceability matrix | |
| 3 Regression suite passes | **Yes**, the Regression-tagged cases | |
| 4 No open critical/high defects | Partly; tests find them | Bug tracker status (Day 3) |
| 5 Accessibility check | No (not in these ACs) | Accessibility scan (Lab 2.3) |
| 6 PO accepts | No | PO review / sprint demo |
